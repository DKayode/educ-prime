# RBAC Permissions Roadmap

This roadmap is the execution order for the next implementation batches. It is intentionally explicit so an agent can follow it without redesigning the authorization model.

## Batch 1 - Done In This Iteration

- Replace controller usages of `RoleGuard` with `RolesGuard`.
- Keep the historical `role.guard.ts` file only for compatibility until a later cleanup.
- Add tests for `RolesGuard`.
- Add the permission model skeleton:
  - `Permission`
  - `@Permissions`
  - `ROLE_PERMISSIONS`
  - `PermissionsGuard`
- Add tests for `PermissionsGuard`.
- Migrate `user-payment` admin wallet routes from `@Roles(RoleType.ADMIN)` to granular `@Permissions(...)`.
- Generate `docs/rbac-route-inventory.md`.
- Document architecture in `docs/rbac-architecture.md`.

## Batch 2 - Protect Obvious Referential Writes (Done)

Use `RolesGuard` first, not `PermissionsGuard`, unless a permission already exists and is clearly mapped.

Target controllers:

- `backend/src/filieres/filieres.controller.ts`
- `backend/src/niveau-etude/niveau-etude.controller.ts`
- `backend/src/series/series.controller.ts`
- `backend/src/types-examen/types-examen.controller.ts`
- `backend/src/filieres-examen/filieres-examen.controller.ts`
- `backend/src/matieres-examen/matieres-examen.controller.ts`
- `backend/src/titre/titre.controller.ts`
- `backend/src/structure/structure.controller.ts`
- `backend/src/categories/categories.controller.ts`
- `backend/src/competences/competences.controller.ts`

Expected rule:

```ts
@UseGuards(JwtAuthGuard, RolesGuard)
@Roles(RoleType.ADMIN)
```

Apply to obvious global writes: `POST`, `PUT`, `PATCH`, `DELETE`, import CSV, and destructive group deletes.

Do not change public or authenticated reads unless the product owner confirms they are sensitive.

## Batch 3 - Migrate Validation Domains To Permissions (Done)

Use `PermissionsGuard` for routes already known to be admin validation workflows.

Target domains:

- `epreuves/submissions`
- `examens-nationaux/submissions`
- `concours/submissions`

Suggested permissions:

- `epreuves.validate`
- `examens_nationaux.validate`
- `concours.validate` if a new concours permission is added

If a domain permission does not exist yet, add it to `Permission` and update tests.

## Batch 4 - Notifications And Stats (Done)

Protect global notification actions and sensitive statistics.

Target controllers:

- `backend/src/notifications/notifications.controller.ts`
- `backend/src/notification-email/notification-email.controller.ts`
- `backend/src/kpi/kpi.controller.ts`
- `backend/src/submissions-stats/submissions-stats.controller.ts`

Use permissions:

- `notifications.send`
- `notifications.cancel`
- `notifications.read`
- `stats.read`

Public unsubscribe endpoints must remain public if they are intentionally public user workflows.

## Batch 5 - User And Authorization Admin (Done)

Persistent permission profiles are now implemented after the first route-protection batches.

Target tables:

- `permission_profiles`
- `permission_profile_permissions`
- `user_permission_profiles`

Keep `utilisateurs.role` unchanged. Do not add organization functions to `RoleType`.

Implemented `AuthorizationService` computes effective permissions from:

- role permissions;
- assigned permission profiles;
- optional future overrides.

`PermissionsGuard` now calls `AuthorizationService` instead of only reading `ROLE_PERMISSIONS`. The service deliberately falls back to `ROLE_PERMISSIONS` if the new tables are not migrated yet, so protected routes do not fail during deployment. Apply `docs/rbac-permission-profiles-migration.sql` in `edukia-db` before using dynamic assignments in production.

Admin endpoints added under `/authorization`:

- `GET /authorization/permissions`
- `GET /authorization/profiles`
- `POST /authorization/profiles`
- `GET /authorization/profiles/:id`
- `PATCH /authorization/profiles/:id`
- `DELETE /authorization/profiles/:id`
- `POST /authorization/users/:userId/profiles`
- `DELETE /authorization/users/:userId/profiles/:profileId`
- `GET /authorization/users/:userId/permissions`

## Batch 6 - Token Revocation For Rights Changes (Done)

Immediate rights revocation is implemented for role changes and permission-profile assignments.

Implemented approach:

- `token_version` is added to `Utilisateur`;
- `tokenVersion` is included in access-token payloads generated by login and refresh;
- `JwtStrategy` compares the token version against the current user version;
- `AuthorizationService` increments `token_version` when permission profiles are assigned or removed;
- `UtilisateursService.update` increments `token_version` when the user role changes.

Apply `docs/rbac-token-version-migration.sql` in `edukia-db`. Full permissions are still not stored in the JWT.

## Verification After Every Batch

Run:

```bash
cd backend
npx jest --runInBand auth/guards/roles.guard.spec.ts
npx jest --runInBand auth/permissions/permissions.guard.spec.ts
npx jest --runInBand auth/strategies/jwt.strategy.spec.ts
npm run build
```

If new permissions are added, update `permissions.guard.spec.ts` or add domain-specific tests.
